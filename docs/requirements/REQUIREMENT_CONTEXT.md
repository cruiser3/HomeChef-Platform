# 家庭私厨点单与饮食协作系统——需求上下文

**文档版本：** V1.2
**用途：** 为项目开发人员和 AI 编程助手提供统一的项目背景、业务目标、已确认需求及待确认事项。
**重要原则：** 本文档中标记为“已确认”的内容可以作为需求依据；标记为“待确认”的内容不得擅自实现为既定规则。

## 1. 项目背景与定位

本项目是一个面向家庭、情侣及熟人小群体的私有点单与饮食协作系统。

系统希望解决家庭内部菜品共享、家庭成员点单、备菜进度协作、食材不足记录和采购清单管理等问题。

本项目不是面向陌生消费者的公开外卖平台，也不是开放式菜品社区。

### 1.1 第一版使用范围

- 仅允许家庭内部成员访问对应家庭的数据。
- 不提供陌生用户搜索或发现家庭的功能。
- 不提供跨家庭点单功能。
- 不提供公开菜品广场。
- 不以支付、配送、商家入驻为第一版目标。

### 1.2 家庭空间架构

采用多个相互独立的家庭空间：

- 系统可以存在多个家庭。
- 每个家庭拥有自己的成员、菜品、订单及相关协作数据。
- 家庭之间的数据相互隔离。
- 用户可以加入多个家庭，并切换当前家庭。
- 用户只能访问自己所属家庭且有权限访问的数据。

## 2. 用户、家庭与角色

### 2.1 用户与家庭关系

已确认：

1. 用户注册后，可以创建家庭，也可以通过邀请码加入已有家庭。
2. 用户可以加入多个家庭。
3. 用户在使用系统时需要切换当前家庭。
4. 用户创建家庭后，自动成为该家庭管理员。
5. 家庭之间完全隔离。

### 2.2 家庭角色

第一版只设置两种家庭角色：

- **管理员：** 拥有家庭管理权限，并拥有已经确认的菜品管理权限。
- **普通成员：** 可以参与家庭菜品、点单和备菜协作等业务。

不单独设置“厨师”“采购员”等权限角色。

成员可以承担不同业务职责，但这些职责不构成独立的系统角色。

### 2.3 邀请机制

已确认：

1. 使用邀请码邀请其他用户加入家庭。
2. 管理员可以生成邀请码。
3. 管理员可以撤销邀请码。

以下规则尚未确认：

- 邀请码有效期。
- 邀请码使用次数（是否只能使用一次、是否允许重复使用）。
- 邀请码的失效规则及使用记录规则（例如撤销后已生成的邀请码如何处理、是否影响已加入成员）。

在这些规则确认前，不要擅自确定邀请码的有效期与使用次数策略。

## 3. 核心业务模块

### 3.1 小家：家庭菜品库

目标：家庭成员可以发布、浏览和管理家庭菜品。

菜品信息初步包括：

- 菜品名称、简介。
- 菜品图片（可选）。
- 菜品分类。
- 制作耗时。
- 食材及用量、单位。
- 单价。
- 制作步骤。
- 步骤文字和图片。
- 菜品创建者。

已确认的菜品权限：

- 创建者可以管理自己创建的菜品。
- 管理员可以管理其他成员创建的菜品。
- 管理员可以修改、下架其他成员的菜品。
- 管理员删除其他成员菜品需要额外限制，但具体限制尚未确定。

注意：

- 菜品创建者信息需要保留。
- 菜品删除规则（已确认）：被历史订单引用的菜品不允许真正删除，只能下架；历史订单必须能够保留原有菜品信息。
- 菜品删除规则（待确认）：未被历史订单引用的菜品是否允许真正删除，尚未确定。
- 菜品是否允许恢复、删除的具体审批规则尚未确定。

### 3.2 下单：家庭内部点单与个人独立购物车

目标：家庭成员通过个人购物车从当前家庭菜品库选择菜品并创建订单。

#### 3.2.1 个人独立购物车（已确认）

第一版采用**个人独立购物车**，不采用家庭共享购物车：

- 购物车属于「用户 + 家庭」的组合，同一用户在不同家庭各自拥有独立购物车；用户 A 在家庭 1、用户 B 在家庭 1、用户 A 在家庭 2 的购物车相互独立。
- 每个家庭成员只能查看和修改自己在当前家庭中的购物车；不同成员之间完全隔离。
- 用户切换家庭后，使用该用户在目标家庭对应的购物车。
- 后端必须校验用户身份及家庭成员资格，不能仅依赖前端传入的 userId 或 familyId。
- 购物车应具有持久化能力，不能仅保存在前端内存中。

购物车第一版功能（已确认）：

1. 将当前家庭菜品库中的可用菜品加入购物车。
2. 修改购物车中菜品的数量。
3. 查看购物车菜品、数量及金额小计。
4. 移除购物车中的菜品。
5. 查看购物车商品总金额。

#### 3.2.2 从购物车提交订单

- 按分类浏览菜品、搜索菜品名称、查看菜品详情（图片、食材、耗时、制作步骤）；家庭成员可以发起点单。

从购物车提交订单时负责（已确认）：

1. 确认购物车内容。
2. 选择就餐时段。
3. 填写订单备注。
4. 提交订单。

购物车与订单的关系（已确认）：

- 加入购物车不创建正式订单；修改购物车不改变订单状态。
- 用户确认提交后，后端才创建正式订单及订单明细。
- 后端必须重新查询菜品信息和价格、重新计算金额，不得信任前端传入的价格。
- 订单创建及订单明细保存必须保证事务一致性。
- 订单明细保存下单时的菜品名称、单价、数量等快照。
- 提交成功后清空本次已提交的购物车内容；提交失败时不得错误清空购物车。

### 3.3 厨房：订单与备菜协作

目标：家庭成员共同处理订单中的菜品。

初步需求：

- 查看当前订单和历史订单。
- 查看订单整体状态。
- 查看订单内每道菜的备菜状态。
- 家庭成员可以标记菜品备菜进度。
- 可以指定某道菜的负责人。
- 默认允许家庭成员共同协作。
- 指定负责人后，其他家庭成员仍然可以更新备菜状态。
- 可以标记开饭状态。

订单整体状态与单道菜的备菜状态应分开设计，不能混为一个字段。

订单取消的基本权限已确认：

- 下单者可以取消自己的订单。
- 管理员可以取消家庭内的订单。

但取消的时间边界尚未确认，特别是订单中部分菜品已经开始备菜时如何处理。

### 3.4 食材不足与家庭采购清单

初步需求：

- 备菜过程中发现食材不足时，可以标记食材不足。
- 记录缺少的食材及数量。
- 将实际缺少的食材加入家庭待购买清单。
- 家庭成员可以查看待购买清单。
- 家庭成员可以标记食材已购买。
- 可以处理误添加的采购记录。

重要边界：

- 只记录实际缺少的食材，不应自动把菜品的全部食材加入采购清单。
- 采购记录应关联相应家庭。
- 食材不足记录与订单、菜品之间的关联方式需要在设计阶段进一步确定。

### 3.5 Home：家庭与个人资料

初步需求：

- 创建和管理家庭。
- 邀请家庭成员。
- 查看家庭成员。
- 管理个人头像、昵称等资料。
- 设置饮食偏好，例如健身、减脂、增肌、清淡、素食等。

第一版收集疾病标签（预置 + 自定义，最多 8 个），仅用于饮食参考、不构成医疗建议；暂不收集用药信息。

## 4. 后续扩展功能

以下功能暂不作为第一版核心交付要求：

1. 从小红书等外部链接导入菜谱。
2. 粘贴菜谱文本，由 AI 整理为制作步骤。
3. AI 饮食搭配建议。
4. 营养和热量估算。
5. 美食广场或外部食材数据源。
6. 更丰富的家庭评论和图片互动。

是否实现应根据第一版核心功能完成情况和剩余时间决定。

AI 营养估算必须明确其为估算结果，不能替代医疗建议。

## 5. 已确认的业务与技术设计注意事项

以下内容是设计时必须考虑的约束：

1. 家庭数据必须隔离。后端不能仅依赖前端传入的 familyId。
2. 用户与家庭采用可支持多对多关系的模型思路，重点考虑 User、Family、FamilyMember。
3. 订单需要保留菜品信息快照。
4. 金额使用 BigDecimal，由后端查询价格并计算。
5. 订单创建及订单明细保存需要事务保障。
6. 订单整体状态和订单菜品备菜状态分开管理。
7. 菜品被历史订单引用时，删除策略不能破坏历史数据。
8. 图片上传需要考虑文件类型、大小、文件名和路径安全。
9. 家庭成员的操作需要校验家庭归属和操作权限。
10. 对多人同时修改订单状态等场景，需要分析并发一致性问题。
11. 购物车按「用户 + 家庭」独立隔离；提交订单时后端重新查询价格并计价，订单与明细事务一致，提交成功后才清空已提交的购物车。

这些注意事项不意味着必须采用某个特定实现。具体实体、字段、接口和技术方案应在需求及设计分析后确定。

## 8. 给 AI 助手的工作约束

1. 开始任务前先阅读本文件及项目已有文档。
2. 严格区分已确认需求、待确认事项和 AI 自己提出的建议。
3. 不得将待确认事项擅自转化为正式业务规则。
4. 发现需求冲突、遗漏或实现风险时，先报告并等待人工确认。
5. 不要为了实现需求而直接重构现有项目架构。
6. 不要擅自修改认证、权限、数据库结构、订单金额计算和删除逻辑。
7. 涉及 Java 代码时，应解释修改原因、关键类和业务流程。
8. 生成的需求和设计文档应有明确版本、状态和验收标准。
9. 所有测试结果必须区分“计划测试”“源码推导的预期结果”和“实际执行结果”。
10. 不得声称没有实际执行的测试已经通过。
