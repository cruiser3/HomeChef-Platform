### D-011：购物车以 `(user_id, family_id, dish_id)` 三元组建模并加唯一约束

- **日期**：2026-11-12
- **决策背景**：实现 M-05 个人独立购物车时，需把 D-009 的「用户 + 家庭」隔离落实到数据模型。
- **当前问题**：购物车行如何建模，才能同时满足「同家庭不同用户隔离」与「同用户不同家庭隔离」，并避免重复添加产生多行。
- **候选方案**：A. 只存 `user_id`，家庭关系运行时再判断；B. 只存 `family_id`，用户维度由查询过滤；C. 行内同时存 `user_id` 与 `family_id`，并建 `(user_id, family_id, dish_id)` 唯一约束。
- **最终选择**：C。
- **选择原因**：A/B 都会让「购物车归属」落在一个维度上，容易出现「按 familyId 查购物车」这类越权入口；C 让两个维度同时固化在数据行上，仓储层可以直接用 `userId + familyId` 双条件查询，且唯一约束天然保证同用户同家庭同菜品只有一条记录，重复添加只需合并数量。
- **对项目的影响**：`cart_items` 表带唯一约束 `uk_cart_item_user_family_dish`；`CartItemRepository` 不提供任何仅按 `familyId` 查询/删除的方法。
- **后续验证方式**：`CartServiceImplTest` 的跨用户、跨家庭隔离用例；启动后 HTTP 实测同家庭双用户互不影响（见 `CART_MODULE.md` 第 8.2 节）。
- **决策状态**：已确定。

### D-012：购物车只引用 `Dish`，价格实时取自服务端且请求体不含价格

- **日期**：2026-11-12
- **决策背景**：需求明确要求「不能相信前端传入的菜品价格，价格应从服务端 Dish 数据中读取」。
- **当前问题**：购物车行是否要存价格快照；请求 DTO 是否保留价格字段。
- **候选方案**：A. 购物车行存下单时刻的价格快照，请求体允许传价格；B. 购物车行只存 `dish_id` 与数量，价格在响应构建时实时从 `Dish` 读取；请求体不含任何价格字段。
- **最终选择**：B。
- **选择原因**：购物车是「待下单的临时清单」，不是成交凭证，价格应始终反映当前菜品价；同时彻底移除请求体价格字段，从接口结构上消除前端传价的可能性，比在服务端做「忽略前端价格」的防御更可靠。真正的价格快照应在 M-06 下单时落入订单明细。
- **对项目的影响**：`cart_items` 无价格列；`AddCartItemRequest`/`UpdateCartItemRequest` 仅含 `dishId` 与 `quantity`；`unitPrice`、`subtotal`、`totalAmount` 全部 `BigDecimal` 且在服务端计算。
- **后续验证方式**：单测「价格始终取自菜品」用例；HTTP 实测改价/下架后购物车金额与状态同步变化（见 `CART_MODULE.md` 第 8.1 节 A19、A24）。
- **决策状态**：已确定。

### D-013：购物车数量范围定为 1~99，下架菜品保留条目但不允许加购/改量

- **日期**：2026-11-12
- **决策背景**：需求只要求「购买数量必须是合法正数」，未给出上限；同时要求「下架菜品不能加入购物车」「修改数量时也必须重新检查菜品状态」。
- **当前问题**：数量上限取多少；菜品下架后，已在购物车中的条目不删除还是自动删除。
- **候选方案**：数量上限 A. 仅要求 ≥ 1 不设上限；B. 设为 1~99。下架处理 A. 自动从购物车移除；B. 保留条目并在响应中标记不可用。
- **最终选择**：数量 1~99；下架菜品保留条目并标记 `dishAvailable=false`，但禁止继续加购与改量。
- **选择原因**：家庭私厨场景单份菜品数量有限，99 足以覆盖且能防止异常大数；下架时保留条目便于用户看到「想买的菜已下架」而不是莫名消失，符合「不擅自扩展复杂功能」的约束，也避免购物车模块反向删除菜品模块的数据。
- **对项目的影响**：`CartServiceImpl` 常量 `MIN_QUANTITY=1`、`MAX_QUANTITY=99`；重复添加合并后同样受 99 限制；`delete` 只在用户显式请求时发生。
- **后续验证方式**：单测数量边界与下架拒绝用例；HTTP 实测数量 0/-2/100 均返回 400，下架后加购与改量均返回 400（见 `CART_MODULE.md` 第 8.1 节 A17~A22）。
- **决策状态**：已确定（若后续业务要求更大数量或下架自动清理，需重新评审）。

### D-015：订单整体状态与单菜备菜状态、开饭状态三套独立存储
