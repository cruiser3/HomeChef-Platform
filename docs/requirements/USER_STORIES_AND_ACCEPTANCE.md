# 第一版需求规格：Epic、User Story、验收标准与测试规格

- **文档版本**：V1.2
- **文档状态**：需求规格初稿（供系统设计、AI 编码与人工验收使用；尚未进入系统设计阶段）
- **创建日期**：2026-11-12
- **修订日期**：2026-11-12（V1.1：展开 90 条测试用例明细、区分预期结果依据、待确认规则与确定验收标准分离、明确订单/备菜/开饭状态概念边界；V1.2：依据人工审查意见修订——管理员取消未开始备菜订单改为待确认、多候选 HTTP 状态码统一标注为待 API 设计确定、补充后续并发场景登记、明确本文档与 API 测试文档的职责边界）
- **需求依据**：`docs/requirements/REQUIREMENT_CONTEXT.md`（V1.2）、`docs/requirements/REQUIREMENT_CODE_GAP_ANALYSIS.md`（V1.2）
- **分解结构**：Epic → User Story → Acceptance Criteria → Test Cases

> **标记规则**：
> - 「已确认」＝来自需求上下文 V1.2 的已确认内容，可作为验收依据。
> - 「待确认」＝需求未定，不得擅自实现（见第 5 节），不得写入确定验收标准。
> - 「建议待人工确认」＝AI 提出的设计建议，不是用户已确认的规则。
> - 「待设计确定」＝属技术/数据模型选型问题，在系统设计或技术设计阶段确定，不阻塞需求澄清。
>
> **预期结果依据（与测试执行状态相互独立）**：
> - `源码推导`：原项目已实现该功能，预期结果由现有源码行为推导而来。
> - `需求规格推导`：原项目未实现或实现不符合要求，预期结果由本文档已确认需求推导而来（不代表代码已具备该行为）。
> - `待确认`：预期结果依赖尚未确认的业务规则（或尚未确定的技术方案），不得作为开发验收依据。
>
> **测试执行状态（独立字段）**：`待执行`、`实际执行通过`、`实际执行失败`。本文档全部 90 条用例当前状态均为 `待执行`；**未实际运行任何测试，不声称任何用例通过**。

> **HTTP 状态码与接口契约的标注规则（与预期依据、执行状态均相互独立）**：
> - 本文档「预期结果」中出现的 HTTP 状态码属于**需求层面的合理预期**，不是最终接口契约。
> - 凡列举多个候选状态码的用例（如 `403/404`、`400/409`、`200/201`），均标注为「**状态码待定**」：业务行为预期保留，具体采用哪一个状态码**留待 API 设计阶段确定**，本文档不提前锁定。
> - 本文档不预设 API URL、请求方法与请求体结构；用例中出现的路径与字段仅为便于理解的示例性表述，不作为接口契约。

## 2. 用户角色与权限约定

- **未登录用户**：仅可注册、登录。
- **家庭管理员**：可管理家庭成员、生成/撤销邀请码、管理（含他人）菜品；菜品删除的权限边界见 U-001/U-007（待确认），本版不授予无条件物理删除权。订单取消方面，需求上下文只确认「管理员可以取消家庭内的订单」这一基础权限（D-REQ-010），而**可取消的时间边界（例如是否限于尚未开始备菜的订单）尚未确认（U-002/U-003）**，因此本版不把「管理员取消尚未开始备菜的订单」列为确定权限规则。
- **家庭普通成员**：可浏览菜品、使用个人购物车、下单、参与备菜协作、记录食材不足。
- **家庭隔离原则**：所有家庭数据访问必须校验「当前用户 + 当前家庭」的成员关系；后端不得只信任前端传入的 `userId`/`familyId`。
- **个人购物车隔离原则**：购物车属于「用户 + 家庭」，成员间相互不可见、不可改。

## 3. Epic 与 User Story 明细

### E-01 用户注册、登录与身份认证

#### US-01-01：用户注册

作为新用户，
我希望通过昵称、邮箱和密码注册账号，
以便获得登录凭证并进入系统。

**验收标准**：

- Given 用户提交合法注册信息（昵称非空、邮箱合法、密码至少 6 位），When 调用注册接口，Then 系统创建账号并返回登录令牌，HTTP 201。
- Given 用户提交已被占用的邮箱，When 调用注册接口，Then 系统拒绝注册并返回冲突错误（409），不创建重复账号。
- Given 用户提交非法邮箱或缺少必填字段，When 调用注册接口，Then 系统返回参数校验错误（400），不创建账号。
- Given 用户在注册请求中自行指定 `ADMIN` 等高权限角色，When 系统处理注册，Then 系统忽略或拒绝该角色，统一按系统默认普通角色创建，避免权限提升。

**关联测试用例**：TC-01-01、TC-01-02、TC-01-03、TC-01-04

#### US-01-02：用户登录

作为已注册用户，
我希望通过邮箱和密码登录，
以便获得访问受保护资源的令牌。

**验收标准**：

- Given 用户提交正确的邮箱和密码，When 调用登录接口，Then 系统返回登录令牌，HTTP 200。
- Given 用户提交错误的密码，When 调用登录接口，Then 系统返回认证失败（401），不泄露具体失败原因。
- Given 用户提交不存在的邮箱，When 调用登录接口，Then 系统返回认证失败（401）。

**关联测试用例**：TC-01-05、TC-01-06、TC-01-07

#### US-01-03：受保护资源需认证

作为系统，
我希望除注册、登录外的接口均要求有效 JWT，
以便防止未认证访问。

**验收标准**：

- Given 请求未携带或携带非法 JWT，When 访问受保护接口，Then 系统返回 401，不返回业务数据。
- Given 请求携带过期 JWT，When 访问受保护接口，Then 系统返回 401（而非 500）。
- Given 请求携带有效 JWT，When 访问受保护接口，Then 系统允许进入并基于当前用户身份处理。

**关联测试用例**：TC-01-08、TC-01-09、TC-01-10

### E-02 家庭空间与成员管理

#### US-02-01：创建家庭

作为注册用户，
我希望创建一个家庭，
以便获得一个独立的数据空间并成为其管理员。

**验收标准**：

- Given 已登录用户提交家庭名称，When 调用创建家庭接口，Then 系统创建家庭并自动将该用户设为该家庭管理员，返回家庭信息。
- Given 已登录用户未提交家庭名称或名称为空，When 调用创建家庭接口，Then 系统返回参数校验错误（400）。
- Given 未登录用户，When 调用创建家庭接口，Then 系统返回 401。

**关联测试用例**：TC-02-01、TC-02-02、TC-02-03

#### US-02-02：切换当前家庭

作为加入多个家庭的用户，
我希望切换当前家庭，
以便在不同家庭间使用各自独立的数据与购物车。

**验收标准**：

- Given 用户是家庭 A、家庭 B 的成员，When 切换到家庭 B，Then 后续家庭数据操作均针对家庭 B。
- Given 用户不是家庭 C 的成员，When 尝试切换到家庭 C，Then 系统拒绝（403/404），不得泄露家庭 C 数据。
- Given 用户切换家庭，When 访问个人购物车，Then 系统返回目标家庭对应的购物车，不得误读原家庭购物车。

**关联测试用例**：TC-02-04、TC-02-05、TC-02-06

#### US-02-03：查看家庭成员

作为家庭成员，
我希望查看当前家庭的成员列表，
以便了解家庭协作成员及其角色。

**验收标准**：

- Given 用户是当前家庭成员，When 查询成员列表，Then 系统返回该家庭成员及其角色（管理员/普通成员）。
- Given 用户不是该家庭成员的访问请求，When 查询该家庭成员列表，Then 系统拒绝（403），不返回成员信息。
- Given 成员角色信息，When 展示成员，Then 仅包含家庭角色（管理员/普通成员），不暴露系统级账号敏感信息。

**关联测试用例**：TC-02-07、TC-02-08

#### US-02-04：家庭数据隔离

作为系统，
我希望严格隔离不同家庭的数据，
以便防止跨家庭越权访问。

**验收标准**：

- Given 用户是家庭 A 成员而非家庭 B 成员，When 访问家庭 B 的菜品/订单/购物车/采购清单，Then 系统一律拒绝（403/404）。
- Given 用户伪造请求中的 `familyId` 为家庭 B，When 后端处理，Then 后端以服务端校验的成员关系为准，拒绝访问，不得只信任前端 `familyId`。
- Given 家庭 A 与家庭 B 拥有同名菜品，When 用户分别查询两个家庭，Then 各自只返回本家庭菜品，互不串数据。

**关联测试用例**：TC-02-09、TC-02-10、TC-02-11

### E-03 邀请码邀请与加入家庭

#### US-03-01：管理员生成邀请码

作为家庭管理员，
我希望生成邀请码，
以便邀请其他用户加入家庭。

**验收标准**：

- Given 当前用户是家庭管理员，When 调用生成邀请码接口，Then 系统生成唯一邀请码并返回给管理员。
- Given 当前用户是普通成员（非管理员），When 调用生成邀请码接口，Then 系统拒绝（403）。

**待确认事项（不计入确定验收标准）**：邀请码有效期（U-005）与使用次数（U-006）尚未确认；本版仅要求「生成唯一邀请码并返回」，不预设有效期与使用次数取值。

**关联测试用例**：TC-03-01、TC-03-02

#### US-03-02：管理员撤销邀请码

作为家庭管理员，
我希望撤销已生成的邀请码，
以便控制成员准入。

**验收标准**：

- Given 当前用户是家庭管理员，When 撤销某有效邀请码，Then 系统使该邀请码失效，后续使用被拒绝。
- Given 当前用户是普通成员，When 尝试撤销邀请码，Then 系统拒绝（403）。

**待确认事项（不计入确定验收标准）**：撤销后的具体影响（已生成码处理、是否影响已加入成员，U-008）尚未确认，不得据此制定确定预期。

**关联测试用例**：TC-03-03、TC-03-04

#### US-03-03：通过邀请码加入家庭

作为注册用户，
我希望通过邀请码加入家庭，
以便成为家庭成员并使用家庭数据。

**验收标准**：

- Given 用户提交有效邀请码，When 调用加入家庭接口，Then 系统将用户添加为该家庭普通成员，返回成功。
- Given 用户提交无效或被撤销的邀请码，When 调用加入家庭接口，Then 系统拒绝加入并返回明确错误。

**待确认事项（不计入确定验收标准）**：
- 用户已是该家庭成员时再次使用邀请码加入，是「拒绝重复加入」还是「幂等处理」，尚未确认（U-009）。本版不擅自选择其中任何一种行为；对应 TC-03-07 的预期依据标记为「待确认」，不作为开发验收依据。
- 邀请码是否允许重复使用（U-006）尚未确认，加入逻辑不得预设使用次数上限。

**关联测试用例**：TC-03-05、TC-03-06、TC-03-07

### E-04 家庭菜品库管理

#### US-04-01：创建菜品

作为家庭成员，
我希望在家庭菜品库中创建菜品，
以便家庭共享可点的菜品。

**验收标准**：

- Given 已登录成员提交合法菜品信息（名称、单价等必填），When 调用创建菜品接口，Then 系统在该家庭创建菜品并记录创建者，返回菜品。
- Given 缺少名称或单价非法（负数/空），When 调用创建菜品接口，Then 系统返回参数校验错误（400）。
- Given 未登录用户，When 调用创建菜品接口，Then 系统返回 401。
- Given 菜品信息含图片、分类、制作耗时、食材（用量+单位）、制作步骤，When 创建，Then 系统保存这些信息（图片上传安全约束见差距分析 7.3）。

**关联测试用例**：TC-04-01、TC-04-02、TC-04-03

#### US-04-02：查看菜品列表与详情

作为家庭成员，
我希望按分类浏览、搜索并查看菜品详情，
以便选择要点的菜。

**验收标准**：

- Given 当前家庭成员，When 查询家庭菜品列表，Then 系统仅返回本家庭菜品。
- Given 菜品名称关键字，When 搜索，Then 系统返回匹配菜品。
- Given 某菜品，When 查看详情，Then 系统返回图片、食材、制作耗时、制作步骤等信息。
- Given 用户不是该家庭成员的访问请求，When 查询该家庭菜品，Then 系统拒绝（403）。

**关联测试用例**：TC-04-04、TC-04-05、TC-04-06

#### US-04-03：修改菜品

作为菜品创建者或家庭管理员，
我希望修改菜品信息，
以便保持菜品库准确。

**验收标准**：

- Given 创建者，When 修改自己的菜品，Then 系统更新并返回成功。
- Given 管理员，When 修改他人菜品，Then 系统更新并返回成功。
- Given 普通成员，When 修改他人菜品，Then 系统拒绝（403）。
- Given 修改后字段非法，When 提交，Then 系统返回参数校验错误（400）。

**关联测试用例**：TC-04-07、TC-04-08、TC-04-09

#### US-04-04：菜品上下架

作为家庭管理员（或创建者管理自己的菜品），
我希望将菜品下架，
以便停止该菜品被继续点单，同时不破坏历史订单。

**验收标准**：

- Given 管理员，When 下架某菜品，Then 系统将该菜品标记为下架，此后不可加入购物车。
- Given 被历史订单引用的菜品，When 尝试删除，Then 系统只允许下架、拒绝物理删除（已确认）。
- Given 管理员，When 下架其他成员菜品，Then 系统允许（已确认：管理员可管理他人菜品）。

**待确认事项（不计入确定验收标准）**：未被历史订单引用的菜品是否允许真正删除（U-007）尚未确认；本版不实现、不验收物理删除路径，菜品对用户可见的「不可点」状态统一由下架表达。

**关联测试用例**：TC-04-10、TC-04-11、TC-04-12

#### US-04-05：菜品分类管理

作为家庭成员，
我希望为菜品设置分类，
以便按分类浏览菜品。

**验收标准**：

- Given 创建/修改菜品，When 指定分类，Then 系统保存菜品分类。
- Given 按分类浏览，When 查询某分类，Then 系统返回该分类下菜品。
- Given 分类的增删改权限与菜品归属一致（创建者/管理员），When 操作，Then 系统做归属校验。

**关联测试用例**：TC-04-13、TC-04-14

#### US-04-06：菜品食材与制作步骤

作为家庭成员，
我希望为菜品维护食材（含用量、单位）和有序制作步骤，
以便备菜与点单参考。

**验收标准**：

- Given 为菜品添加食材，When 提交食材名称、用量、单位，Then 系统保存食材及用量单位。
- Given 为菜品添加多个制作步骤，When 提交有序步骤，Then 系统保存步骤顺序。
- Given 修改菜品，When 更新食材或步骤，Then 系统更新对应信息。

**待设计确定（不计入确定验收标准）**：食材是否作为可复用字典（Q-4）属数据模型设计问题，本版不预设；无论采用哪种方案，均须满足上述「保存用量与单位、保存步骤顺序」的验收要求。

**关联测试用例**：TC-04-15、TC-04-16、TC-04-17

### E-05 个人独立购物车与家庭点单

> 职责划分（已确认）：购物车负责「添加菜品、修改数量、查看菜品与金额小计、移除菜品、查看商品总金额」；从购物车提交订单时负责「确认购物车内容、选择就餐时段、填写订单备注、提交订单」。

#### US-05-01：将菜品加入购物车

作为家庭成员，
我希望将当前家庭菜品库中的可用菜品加入自己的购物车，
以便后续统一确认和提交订单。

**验收标准**：

- Given 当前家庭成员，When 将本家庭可用菜品加入购物车，Then 系统将该菜品加入该用户在「当前家庭」的购物车。

### E-06 订单管理与备菜协作

> **状态概念边界（本版只定义概念边界，不确定最终枚举与完整状态机）**
>
> 1. **订单整体状态**：描述「一张订单」的整体进度，是订单级别的单一状态，用于订单列表筛选、整单取消等整单级判断。
> 2. **单道菜备菜状态**：挂在订单明细（每道菜）上的独立状态，描述该道菜自身的备菜进度；同一订单内多道菜可处于不同进度。
> 3. **开饭状态**：描述「这顿饭是否可以开饭」的独立标记，语义上既不等同于订单整体状态，也不等同于任何一道菜的备菜状态。
>
> 边界约定：
> - 单道菜备菜状态**不能直接替代**订单整体状态；订单整体状态不得由某一道菜的状态机械推导得出。
> - 开饭状态的具体归属（订单级字段，还是独立的开饭记录）及其与其余两个状态的联动方式，**需要在系统设计阶段确定**，本版不预设。
> - 并发状态更新方案（乐观锁、状态版本号、状态机校验等）**需要在技术设计阶段确定**，本版不预设具体机制。
> - 本版不定义三者的最终状态枚举与状态机；枚举取值在系统设计阶段给出，且必须满足「三概念分别存储、互不替代」这一已确认要求。

#### US-06-01：查看订单

作为家庭成员，
我希望查看当前和历史订单及每道菜的备菜状态，
以便了解点单与备菜进度。

**验收标准**：

- Given 当前家庭成员，When 查看本家庭订单列表/详情，Then 系统返回订单整体状态、每道菜各自的备菜状态、以及独立的开饭状态标记，三类信息互不替代。
- Given 用户访问非本家庭订单，When 查询，Then 系统拒绝（403）。
- Given 订单详情，When 展示，Then 金额为后端计算/快照值，不信任前端传入金额。

**关联测试用例**：TC-06-01、TC-06-02、TC-06-03

作为下单者或家庭管理员，
我希望取消订单，
以便处理不再需要的订单。

**验收标准**：

- Given 下单者且订单尚未开始备菜，When 取消自己的订单，Then 系统取消该订单（已确认）。
- Given 非下单者且非管理员，When 取消他人订单，Then 系统拒绝（403，状态码待定）。

**待确认事项（不计入确定验收标准）**：

- **管理员取消「尚未开始备菜」订单是否成立**：需求上下文只确认「管理员可以取消家庭内的订单」这一基础权限（D-REQ-010），但明确「取消的时间边界尚未确认」（`REQUIREMENT_CONTEXT.md` 3.3 节）。因此「管理员可以取消尚未开始备菜的订单」**不是已确认规则**，本版不将其写入确定验收标准，也不反向断定管理员不能取消；管理员的实际可取消范围随 U-002、U-003 一并确认。
- 部分菜品开始备菜后能否取消（U-002）保持待确认。
- 管理员取消已开始备菜订单的具体规则（U-003）保持待确认。
- 取消后采购清单如何处理（U-004）保持待确认。

> 备注：本版确定验收标准只覆盖「下单者取消自己尚未开始备菜的订单」以及「非下单者且非管理员的越权取消被拒绝」两项；管理员一侧的取消范围在 U-002/U-003 确认前不作为开发验收依据，对应 TC-06-05 的预期依据标记为「待确认」。

### 6.3 状态概念的处理结论

订单整体状态、单道菜备菜状态、开饭状态三个概念已在 E-06 开头明确定义边界并确认「分别建模、分别存储、互不替代」。但三者的**最终状态枚举、开饭状态归属、联动规则、并发更新机制**均未在本版确定，须在系统设计（归属与联动）与技术设计（并发控制）阶段解决。本版不构成状态机设计。
